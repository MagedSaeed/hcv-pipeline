# Analyses Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give system analysts a saved, four-step flow (System, Generate, Label, Report) that runs the research's recommended setup on their own system.

**Architecture:** A new Django app `analyses` with its own tables and a one-task-per-model-call runner. It shares the renderer, schemas, LLM client, taxonomy and login with the research app and writes no research rows. The React app gets an `/analyses` area on a small JSON API.

**Tech Stack:** Django 5.2, DRF, django-q2, pytest; React 19, react-query, Tailwind 4, vitest + msw. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-22-analyses-design.md`. Read it with this plan: it holds the screen copy, the 19-row threat table and the display rules, which are not repeated here.

## Global Constraints

- Branch `analyses`, from `main` at `0620f6c`. Never push, merge or tag without the owner's word.
- Commit only if the owner allowed it at handoff. One-line message, no co-author trailer, explicit paths. Otherwise each task ends as an uncommitted checkpoint.
- Baseline to keep: 1230 backend tests, 270 frontend tests. Ruff has 12 existing errors: add none, fix none.
- Analyses creates no `Experiment`, `PipelineRun`, `PhaseRun`, `SystemDescription`, `Scenario`, `LLMCall` or `Label` row.
- Research prompts render byte for byte as before.
- Defaults: `anthropic/claude-sonnet-5`, 0.8, "Zero-shot Variant B" v1, no examples, 8 scenarios; `openai/gpt-5.6-luna-pro`, 0.0, "default-labelling" v1, the five examples; HCV-21 v1.2.
- Limits: description 50,000 characters; count 1 to 20; 30 included scenarios; temperature 0 to 2; one queued or running run per analysis.
- Temperature is always editable. The hint reads exactly "This model may ignore temperature".
- The tag reads exactly "Added manually" and never reaches the labeller.
- Users and accounts stay as they are: signed-in users read, staff write and run.
- Schema changes must let the code at `0620f6c` keep writing: a new column on an existing table is nullable or has a `db_default`.
- Comments and docstrings: one or two lines, what and why, describing only what exists.
- No test or check makes a provider call. A live run needs the owner's consent to the cost.

## Review Focus

1. A description containing `{{ ... }}`, `{% ... %}` or braces: sent literally, never evaluated (Task 5).
2. A double click or second tab on Generate or Label: one run, one bill, and a clear "already running" (Task 5).
3. A truncated, non-JSON or empty reply to "Generate again": the previous scenarios and labels survive (Task 6).
4. Arabic or mixed-direction text: sent intact and displayed with `dir="auto"` (Tasks 6 and 8).
5. Leaving System, or clicking Generate, within the autosave delay: the last keystrokes are saved first (Task 8).

### Task 6: The runner

**Files:**
- Create: `backend/analyses/runner.py`
- Test: `backend/analyses/tests/test_runner.py`

**Interfaces:**
- Consumes: `pipeline.clients.get_llm_client`, `pipeline.failures.describe_failure` and `describe_provider_error`, `llm.schemas` parse, schema and `split_known_labels` helpers.
- Produces: `execute(run_id, position) -> str`.

Algorithm:
1. Claim with a conditional update `(status=queued, position) -> running` and set `progressed_at`. No row means a duplicate, cancelled or deleted task: return.
2. Render from `pinned` and call the provider outside any transaction.
3. In a transaction, `select_for_update` the run. Gone or no longer running: save nothing.
4. Save the call and its result. Last position: finish (failed if any failed). Otherwise set `queued` at `position + 1` and enqueue on commit, so waiting behind research work cannot look stuck. A failed enqueue fails the run.

Saving a generation: only a parsed, non-empty reply replaces anything. Delete generated rows, keep manual ones, renumber duplicate or colliding ids, set aside what exceeds 30 with a notice, note a count differing from the request.
Saving labels: replace that scenario's labels, then set `label_key` and `labelled_call`. An empty list is a success. The key is the one for what was sent.

## Release and going back (each step on the owner's word)

Pushing `main` deploys to Railway.

1. Check production has no taxonomy v1.2 (spec section 4) and take a database dump into `railway_db_dumps/`.
2. `git tag before-analyses <main's commit just before the merge>`, then push the tag.
3. `git switch main && git merge --no-ff analyses`, then push.

To go back: `git revert -m 1 <merge commit>` and push. This redeploys the old code without rewriting history. To return, revert that revert.

The database stays migrated, which the old code tolerates: the new columns accept its inserts and it ignores the new tables. While reverted, two limits apply: queued analysis tasks fail harmlessly, and deleting a user who owns an analysis is refused by the database.
