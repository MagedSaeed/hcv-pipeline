# Frontend Implementation Plan (plan 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A React SPA that lets the researcher tune prompts cheaply, launch experiments, watch them run, and read the result — the ten screens of spec §10.

**Architecture:** Vite + React 19 SPA talking to the existing DRF backend over session auth with CSRF. React Query owns all server state; there is no client-side store. React Router provides the shell; every screen is a route. Tailwind 4 (CSS-first, no config file) provides styling.

**Tech Stack:** Node 24.20.0 LTS, react/react-dom 19.2.8, vite 8.2.2, react-router-dom 7.18.3, @tanstack/react-query 5.102.8, axios 1.20.0, tailwindcss 4.3.3. Tests: vitest, @testing-library/react, @testing-library/user-event, msw.

**Spec:** `docs/superpowers/specs/2026-09-07-hcv-pipeline-design.md` — §10 (Screens) is binding and was rewritten on 2026-09-10 to match the current backend. §3 pins the stack; §9 is the API contract.

**Builds on:** the backend, complete at 920 tests across plans 1, 2, 3a, 3b and iterate mode.

## Global Constraints

- **Node 24.20.0 LTS**, **npm** (not pnpm or yarn). Pin every dependency to the exact version in spec §3 — no `^` or `~` ranges. `npm ci` must be reproducible.
- All frontend work lives in `frontend/`. Never modify `backend/` from a frontend task; if the API is missing something, **stop and report it** rather than working around it client-side.
- **Tailwind 4 is CSS-first.** There is no `tailwind.config.js`; configuration lives in CSS via `@theme`. Do not create one.
- **Session auth, not tokens.** `axios` must send `withCredentials: true`, fetch `GET /api/auth/csrf/` before the first unsafe request, and send `X-CSRFToken`. There is no JWT anywhere in this system.
- **React Query owns server state.** No Redux, no Zustand, no context for server data. Context is only for the authenticated user.
- **Never store a secret in the frontend.** The OpenRouter key is set and read through the backend; the Settings screen shows only the masked value the API returns.
- Tests are **vitest + React Testing Library + msw**. Mock at the **network** boundary with msw, never by stubbing modules — the point is to exercise the real client code, and a fake that is more permissive than the API is exactly how a whole broken call path passed 760 backend tests earlier in this project.
- Run `npm run lint` and `npm run test` before finishing any task; both must be clean.
- Do not commit or stage; leave changes unstaged.

## Domain rules the UI must respect

These are not cosmetic. Each one exists because of something the backend enforces.

- **Generated material is immutable.** Rows with `origin: "generated"` are read-only. Show them as read-only *and say why* — "generated by a run; change the prompt or inputs and generate again" — rather than silently disabling a field.
- **Iterate-mode runs are scratch.** They are never archived and never appear in an export. Any screen that starts or lists one must say so plainly, or a researcher will assume their tuning runs are part of the record.
- **Variant A never sees the taxonomy.** The preview endpoint renders A's real context, which has no `taxonomy` key. The UI must never synthesise a preview client-side, never "helpfully" fill in the taxonomy for an A preview, and never hide a preview error — an error there is the guarantee working.
- **Cancel does not interrupt a worker.** Wherever cancel is offered, repeat the backend's caveat: it marks a run dead so it can be deleted; a worker already mid-call may still finish and write.
- **Pinned config is not current config.** Run detail shows what a repetition *used*, which can differ from the experiment's current settings. Label them distinctly; never show one where the other belongs.

## File Structure

```
frontend/
  package.json  vite.config.js  index.html
  src/
    main.jsx  App.jsx  index.css
    api/          client.js (axios + CSRF), queries.js (React Query hooks)
    contexts/     AuthContext.jsx
    components/   Layout, ProtectedRoute, StatusBadge, ProgressBar, EmptyState,
                  ErrorBanner, ConfirmDialog, CodeBlock
    pages/        Login, Settings, Dashboard, Resources, Taxonomy, Corpus,
                  PromptEditor, ExperimentBuilder, RunDetail, Labels
    test/         setup.js, server.js (msw handlers), factories.js
```

**Why `api/queries.js` is one module:** every screen needs the same cache keys, and a key typed differently in two places is a stale-data bug that looks like a backend problem. One module owns the keys.

### Task 1: Scaffold, API client, auth

**Files:** `frontend/` (new), `src/api/client.js`, `src/contexts/AuthContext.jsx`, `src/components/ProtectedRoute.jsx`, `src/pages/Login.jsx`, `src/test/{setup,server}.js`

**Interfaces:**
- Produces: `apiClient` (axios instance), `useAuth()`, `<ProtectedRoute>`, the msw test server.

- [ ] **Step 1: Scaffold with pinned versions**

`npm create vite@latest frontend -- --template react`, then pin every version from spec §3 exactly. Add Tailwind 4 via `@tailwindcss/vite`, configured in `src/index.css` with `@import "tailwindcss"` and an `@theme` block — **no `tailwind.config.js`**. Add vitest, `@testing-library/react`, `@testing-library/user-event`, `jsdom`, `msw`. Configure `vite.config.js` to proxy `/api` to `http://localhost:8000` in dev.

- [ ] **Step 2: Write the failing auth tests**

`src/pages/__tests__/Login.test.jsx`, with msw handlers for `GET /api/auth/csrf/`, `POST /api/auth/login/`, `GET /api/auth/me/`:

- submitting valid credentials calls `csrf` **before** `login`, then lands on the dashboard
- an invalid password shows the API's error message, and the user stays on Login
- an unauthenticated visit to a protected route redirects to Login
- a user with `must_change_password` is sent to the change-password screen and **cannot** navigate away
- logging out clears the cached user, so a protected route redirects again

- [ ] **Step 3: Implement**

`client.js`: an axios instance with `withCredentials: true` and a request interceptor that fetches and caches the CSRF token before the first unsafe method, then sets `X-CSRFToken`. A response interceptor turns a 401 into a redirect to Login and clears the React Query cache. **Do not** retry 401s.

`AuthContext.jsx`: wraps `GET /api/auth/me/` in React Query; exposes `user`, `isStaff`, `login`, `logout`. `ProtectedRoute` waits for that query to settle before deciding — redirecting while it is still loading logs the user out on every refresh.

- [ ] **Step 4: Verify** — `npm run test` and `npm run lint` clean.

Status colours live in `StatusBadge` alone: pending/queued neutral, running active, completed positive, failed negative, **cancelled distinct from failed** — an operator who cancelled a run must not read it as a crash.

### Task 5: Prompt editor and the iterate panel

The largest screen, and the one the researcher lives in. Spec §10 describes it in detail — read that section before starting.

**Files:** `src/pages/PromptEditor.jsx`, `src/components/CodeBlock.jsx`

- [ ] **Step 1: Failing tests**
- lists templates by phase, and for phase 2 makes the **variant explicit** — A and B are separate templates
- editing creates a **new version**; history is listed and older versions are viewable
- preview renders against the selected variant's real context via the preview endpoint
- **a variant-A template referencing `taxonomy` shows the render error rather than a preview** — assert the error text is visible, and that no preview is shown
- the same template body previews successfully for B
- saving is blocked while preview reports an error, and the reason is shown
- the iterate panel: pick an experiment to borrow from, override counts, run, and see status; the panel states these runs are **not archived**
- an iterate run that fails shows the API's error

- [ ] **Step 2: Implement**

Validation before save is the point of this screen, not a nicety: templates render under `StrictUndefined`, so a mistake in the A template fails only the A run while B succeeds — the most confusing symptom the system produces. Preview each variant and refuse to save on error.

The iterate panel posts to `POST /api/phase-runs/` and polls that phase run. Show the rendered prompt and the raw response side by side when it finishes.

- [ ] **Step 3: Verify.**
