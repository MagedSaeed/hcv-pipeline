# Frontend Implementation Plan (plan 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A React SPA that lets the researcher tune prompts cheaply, launch experiments, watch them run, and read the result — the ten screens of spec §10.

**Architecture:** Vite + React 19 SPA talking to the existing DRF backend over session auth with CSRF. React Query owns all server state; there is no client-side store. React Router provides the shell; every screen is a route. Tailwind 4 (CSS-first, no config file) provides styling.

**Tech Stack:** Node 24.20.0 LTS, react/react-dom 19.2.8, vite 8.2.2, react-router-dom 7.18.3, @tanstack/react-query 5.102.8, axios 1.20.0, tailwindcss 4.3.3. Tests: vitest, @testing-library/react, @testing-library/user-event, msw.

**Spec:** `docs/superpowers/specs/2026-09-07-hcv-pipeline-design.md` — §10 (Screens) is binding and was rewritten on 2026-09-10 to match the current backend. §3 pins the stack; §9 is the API contract.

**Builds on:** the backend, complete at 920 tests across plans 1, 2, 3a, 3b and iterate mode.

## Global Constraints

- **Node 24.20.0 LTS**, **npm** (not pnpm or yarn). Pin every dependency to the exact version in spec §3 — no `^` or `~` ranges. `npm ci` must be reproducible.
- All frontend work lives in `frontend/`. Never modify `backend/` from a frontend task; if the API is missing something, **stop and report it** rather than working around it client-side.
- **Tailwind 4 is CSS-first.** There is no `tailwind.config.js`; configuration lives in CSS via `@theme`. Do not create one.
- **Session auth, not tokens.** `axios` must send `withCredentials: true`, fetch `GET /api/auth/csrf/` before the first unsafe request, and send `X-CSRFToken`. There is no JWT anywhere in this system.
- **React Query owns server state.** No Redux, no Zustand, no context for server data. Context is only for the authenticated user.
- **Never store a secret in the frontend.** The OpenRouter key is set and read through the backend; the Settings screen shows only the masked value the API returns.
- Tests are **vitest + React Testing Library + msw**. Mock at the **network** boundary with msw, never by stubbing modules — the point is to exercise the real client code, and a fake that is more permissive than the API is exactly how a whole broken call path passed 760 backend tests earlier in this project.
- Run `npm run lint` and `npm run test` before finishing any task; both must be clean.
- Do not commit or stage; leave changes unstaged.

## Domain rules the UI must respect

These are not cosmetic. Each one exists because of something the backend enforces.

- **Generated material is immutable.** Rows with `origin: "generated"` are read-only. Show them as read-only *and say why* — "generated by a run; change the prompt or inputs and generate again" — rather than silently disabling a field.
- **Iterate-mode runs are scratch.** They are never archived and never appear in an export. Any screen that starts or lists one must say so plainly, or a researcher will assume their tuning runs are part of the record.
- **Variant A never sees the taxonomy.** The preview endpoint renders A's real context, which has no `taxonomy` key. The UI must never synthesise a preview client-side, never "helpfully" fill in the taxonomy for an A preview, and never hide a preview error — an error there is the guarantee working.
- **Cancel does not interrupt a worker.** Wherever cancel is offered, repeat the backend's caveat: it marks a run dead so it can be deleted; a worker already mid-call may still finish and write.
- **Pinned config is not current config.** Run detail shows what a repetition *used*, which can differ from the experiment's current settings. Label them distinctly; never show one where the other belongs.

## File Structure

```
frontend/
  package.json  vite.config.js  index.html
  src/
    main.jsx  App.jsx  index.css
    api/          client.js (axios + CSRF), queries.js (React Query hooks)
    contexts/     AuthContext.jsx
    components/   Layout, ProtectedRoute, StatusBadge, ProgressBar, EmptyState,
                  ErrorBanner, ConfirmDialog, CodeBlock
    pages/        Login, Settings, Dashboard, Resources, Taxonomy, Corpus,
                  PromptEditor, ExperimentBuilder, RunDetail, Labels
    test/         setup.js, server.js (msw handlers), factories.js
```

**Why `api/queries.js` is one module:** every screen needs the same cache keys, and a key typed differently in two places is a stale-data bug that looks like a backend problem. One module owns the keys.

- [ ] **Step 2: Write the failing auth tests**

`src/pages/__tests__/Login.test.jsx`, with msw handlers for `GET /api/auth/csrf/`, `POST /api/auth/login/`, `GET /api/auth/me/`:

- submitting valid credentials calls `csrf` **before** `login`, then lands on the dashboard
- an invalid password shows the API's error message, and the user stays on Login
- an unauthenticated visit to a protected route redirects to Login
- a user with `must_change_password` is sent to the change-password screen and **cannot** navigate away
- logging out clears the cached user, so a protected route redirects again

- [ ] **Step 3: Implement**

`client.js`: an axios instance with `withCredentials: true` and a request interceptor that fetches and caches the CSRF token before the first unsafe method, then sets `X-CSRFToken`. A response interceptor turns a 401 into a redirect to Login and clears the React Query cache. **Do not** retry 401s.

`AuthContext.jsx`: wraps `GET /api/auth/me/` in React Query; exposes `user`, `isStaff`, `login`, `logout`. `ProtectedRoute` waits for that query to settle before deciding — redirecting while it is still loading logs the user out on every refresh.

- [ ] **Step 4: Verify** — `npm run test` and `npm run lint` clean.

### Task 10: Fix round from the final review and the walkthrough

Nine tasks each passed their own review; the whole-plan review found what falls between them.
The findings below are all probe-confirmed unless marked PLAUSIBLE. No user decision was needed —
every item is a defect or an obvious gap-fill. Walkthrough (task 9) findings are appended as they
arrive and fold into these sub-tasks.

**Sequencing rule (from today's concurrency incident):** at most one frontend agent and one
backend agent at a time, never two in the same tree, and every commit stages explicit paths with
the staged set verified. 10.1 goes first because nearly every other sub-task builds on
`frontend/src/api/queries.js`.

- [ ] **10.1 — Pagination everywhere, and mocks that paginate (frontend; do first)**

Every list hook except `useAllLabels` makes one GET through `fetchList` and reads only page one,
and a comment in `queries.js` calls that "the house style" — contradicting spec §9 ("follow
`next`"). Confirmed consequences: Labels **rows** (a probe drew 50 of 60 scenarios; labels for
rows 51+ were fetched and never shown), prompt picker and history, the builder's prompt, seed and
target selects, Corpus, the Run-detail call inspector, the phase-3 scenario picker, and the
Dashboard's run list and poll gate (repetitions 51-100 keep running after polling stops).

Rule, replacing the comment: **no screen may present a partial list as complete.** Either fetch
every page, or paginate visibly with a total ("50 of 212") and a pager. Fetch-all is the default;
choose visible paging only where a realistic list is too large to hold, and say which in a comment.
Resolve the `useLabels`/`useAllLabels` cache-key collision so one key never has two fetchers.

The bug survived because only one mock in the suite ever returns a second page. Add a shared msw
helper that paginates **every** list handler exactly as DRF does (`PAGE_SIZE = 50`, `count`,
`next`, `previous`), give each affected screen a fixture larger than 50, and verify each test
fails when its hook is reverted to a first-page read. Also: make `errors.js` read bare-string field
errors as well as lists (some views raise them); and, PLAUSIBLE, have shared mocks enforce
`X-CSRFToken` on unsafe methods and return 403 for non-staff writes where the real API does.

- [ ] **10.2 — Results correctness (frontend + small backend)**

Labels draws its columns from the **active** taxonomy rather than the one pinned on the labelling
phase run, so activating a new version later shows old runs under the wrong vocabulary and silently
drops labels on retired HCVs. Use the pinned taxonomy; if the phase runs being shown pinned
different taxonomies, say so plainly instead of merging them. Add a Run detail → Labels link with
the run preselected (today the run id must be typed). Retry must invalidate the pipeline run and its
progress, not only the phase runs; and on the backend, a repetition fully repaired by retry must be
rolled up out of FAILED — `finish_labelling_run` never rolls up today.

- [ ] **10.3 — Experiment lifecycle in the UI (frontend + spec §10)**

An experiment can only be launched from builder state in the moment after it is created. The
builder's own 503 `missing_api_key` hint ("Go to Settings") unmounts that state, there is no
`/experiments/:id` route, Dashboard rows are not links, and names are unique — so the experiment is
stranded. Add an **Experiment detail** screen: its current configuration (labelled as current, not
pinned), launch N repetitions with the help text from `OPTIONS`, its runs linking to Run detail, and
Edit reusing the builder form via PATCH. Dashboard rows link to it and the builder lands on it after
create. Add the screen to spec §10.

- [ ] **10.4 — A template can only run as the variant it was validated for (frontend + backend)**

`loadVersion` never resets the preview variant and templates store none, so after previewing a B
template, an A-intended one referencing `taxonomy` previews clean under the stale "B", saves, and
is accepted as `phase2_prompt_a`. Nothing leaks — the choke point refuses at run time — but only
after variant B's paid calls have already been spent, which is exactly what validate-before-save
exists to prevent.

- Frontend: the variant cannot go stale — reset it on loading a template, and gate Save on a
  successful preview of **this** draft under the chosen variant.
- Remove the green "Preview OK — isolation scan did NOT run" state. A variant-A preview whose scan
  did not run is never OK. It is dead code today only because the mock returns 200 where the real
  endpoint fails closed with 400; make the mock match.
- Backend: at launch, dry-render each active variant's phase-2 template under **its own** variant
  context with the experiment's real inputs, and refuse with a 400 on the right field and **zero
  provider calls** if it fails. This keeps the researcher's two-independent-templates design
  without adding a field to templates.

- [ ] **10.5 — Scratch material is recognisable everywhere (backend + frontend)**

Iterate-run output is labelled as scratch only under Corpus `?phase_run=`; corpus rows carry no
`generation_run`, so unfiltered Corpus and the pickers show scratch as ordinary generated rows, and
no UI can delete a phase run. Backend: expose `generation_run` and an `is_scratch` flag (generated
by a phase run with no `pipeline_run`) on corpus serializers. Frontend: mark scratch rows wherever
they appear; offer only seed and manual origin in the builder's seed and target pickers (the backend
refuses generated ones anyway); allow deleting an iterate run; show isolation evidence
(`leak_scan_ran` / `guarded_by`) in the iterate panel.

- [ ] **10.6 — Small items**

The choke-point message says the taxonomy has no usable rows when the rule refuses on **any** blank
row — say that. Session expiry is detected by matching DRF's English `detail`; add a
machine-readable `code` to auth and permission error bodies on the backend and branch on it.

**Walkthrough (task 9) results, folded in.** All ten screens were driven in real headless Chrome
against real Django and a real worker; the runbook worked exactly as written, with zero wrong or
missing steps; the one paid call cost $0.057. Findings:

- *(10.2)* **A spurious 404 after deleting a run.** A pending refetch of the deleted run resolves
  just after the DELETE succeeds, before the redirect. No visible impact, but cancel and remove
  that run's queries on delete success rather than leaving them to race the navigation.
- *(10.6)* **Settings cannot clear an admin-entered key.** Save disables on an empty field, so once
  a key is saved there, the UI can never fall back to `.env`. The API already allows it
  (`openrouter_key` is `allow_blank=True`), so this is a frontend change: an explicit, confirmed
  "clear — use the environment key" action. Add the backend test that clearing works, which is
  currently untested.
- *(runbook)* Added a warning that a key saved in Settings outranks `.env` — the exact trap that
  failed the walkthrough's first iterate attempt with a 401.
